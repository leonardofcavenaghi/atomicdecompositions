# Software version comparison

Choose an individual flag or toric distribution, or the combined application with separate workspaces. The versions below differ in their geometric inputs, execution tools and analysis capabilities.

Flag **1.0.6.dev0** and flag, toric and combined **1.1.0.dev1** are development distributions. Stable flag **v1.0.5** remains available for archived calculations.

See [Input and output conventions](input-output.md) for exact formats and [Validation and reproducibility](launch-plan.md) for verification scope.

## 1. The software choices

| Offering | Primary use | Distribution and launch |
|---|---|---|
| Flag program 1.0.6.dev0 | Flag workflow with updated parameter names, empty-insertion CLI handling and tree generation | gwflags source; python -m gwflags.gui |
| Flag engine 1.1.0.dev1 | Flag computations plus checkpointed execution, supported Hodge calculations and connection analysis | Individual flag source bundle; standalone flag GUI, or enhanced /flag/ workspace in the combined bundle |
| Toric engine 1.1.0.dev1 | Explicit fans, toric constructors, toric cohomology and supported complete intersections | Individual toric source bundle or combined source; python -m gwtoric.gui |
| Combined application | Choose flag or toric calculations from one local application | Complete gw-combined source; python -m gwapp |
| Preserved original flags | Reproduce archived calculations using the original runtime and parameter names | v1.0.5 runtime and archived guide |

Individual 1.1.0.dev1 source distributions include the shared execution infrastructure but omit the combined launcher. The combined distribution includes both engines and the enhanced workspaces.

The combined application retains separate geometric inputs, curve-coordinate models and computation engines.

## 2. Mathematical and practical differences

| Capability | Flags 1.0.6.dev0 | Flags 1.1.0.dev1 | Toric engine 1.1.0.dev1 |
|---|---|---|---|
| Ambient description | Root system and kept roots | Same flag model | Rays and maximal cones; product, split projective-bundle and blow-up constructors |
| Cohomology classes | Schubert classes | Same flag classes | Divisor polynomials modulo fan relations |
| Curve coordinates | Nonnegative kept-root coroot degrees | Same flag coordinates | Integral ray relations or displayed H2 basis; negative relation entries are allowed |
| Twisting bundles | Supported convex homogeneous bundles, including tautological constructions and operations | Retains that bundle API | Sums of supported nontrivial nef line bundles |
| Quantum API result | Matrix, grading, Schubert basis indices | Same flag result convention | Matrix, grading, basis names |
| General runtime Hodge module | No | Ambient flags and supported ample line-bundle intersections | Ambient toric diamonds; supported ample Fano CIs in dimensions 3–5 |
| Durable flag progress | Original execution path | Available through the execution wrapper and enhanced workspace | Separate toric execution/checkpoint infrastructure |
| Exact connection analysis | Existing spectrum tools | Added supported exact cyclicity and exponent analysis | Toric connection/spectrum tools with their own supported cases |

Flag version 1.1.0.dev1 builds directly on the flag 1.0.x implementation. The differences concern execution and analysis as well as the added toric geometry. The exact genus-zero localization framework and existing supported bundle semantics remain the reference for the flag calculations.

All complete-intersection quantum matrices must be interpreted on their returned ambient sector. Computing a full Hodge diamond does not construct the missing primitive quantum multiplication. Automatic curve lists also have a scope: a conditional Mori search or degree cutoff must not be presented as an unconditional complete quantum operator.

## 3. Parameter naming

The default flag convention is named `paper`:

- Type A examples retain ambient node names. A4 with keep 2 uses y2; A2xA4 with keep 1,3 uses y1 and y3.
- Other families use consecutive parameters in entered kept-root order. C3/keep 3, G2/keep 2 and D5/keep 4 therefore use y1.
- Mixed-family targets use the same consecutive rule; the explicit returned map is authoritative.

The compatibility convention ambient preserves the previous names. Compact requests consecutive names in every family. The choice is available through the Python constructor, the flag CLI and the flag interface.

```python
from gwflags import FlagVariety

paper = FlagVariety("C2", [2])
legacy = FlagVariety("C2", [2], novikov_convention="ambient")
assert paper.novikov_names == ("y1",)
assert legacy.novikov_names == ("y2",)
```

This is a parameter relabeling. It preserves beta coordinates, exact coefficients, basis ordering and grading. Results record the selected convention and node-to-parameter map. Existing catalog matrices retain their original labels; use ambient when comparing with those archives.

Toric parameter names are retained. They follow the reported Novikov divisor basis, which can differ from the cohomology divisor basis used by short K rows.

## 4. Empty CLI insertions now mean no insertions

A blank insertion list is valid. The unmarked cubic-surface line invariant is 27; it needs no point insertion.

The Python API and original flag interface already behaved correctly. The old flag CLI interpreted empty text as a unit insertion. Both current flag CLIs now return an empty list for blank text, matching Python and the interface.

```bash
python -m gwflags.cli A3 --keep 1 -K 3 gw --beta 1 --classes ""
```

The result is 27. The corresponding unmarked quintic call returns 2875. An explicit id/e in flag mode, or one in toric mode, still denotes a unit insertion. The preserved v1.0.5 CLI retains its historical behavior and is identified accordingly in the archived guide.

## 5. Faster unmarked tree generation

Both current flag versions use the rooted-shape generator from revision `7f167e1`. It enumerates rooted shapes, groups equivalent free shapes using AHU, and then selects the legacy lexicographic representatives.

Independent checks established exact representative edges, vertex labels and ordering through six edges. Existing checkpoint tree numbers remain compatible in the tested range. This update improves graph generation while retaining the localization contributions and marking conventions.

## 6. Exact large-fraction checkpoints

The enhanced flag execution path saves exact intermediate fractions. Very large numerators or denominators could make the old decimal writer exceed Python's integer-to-string conversion limit.

The new writer stores large values as tagged hexadecimal numerator/denominator integers. Exact signs and rational values are preserved, and ordinary legacy decimal checkpoints remain readable. The interpreter's global conversion limit is left unchanged.

Newly tagged values require the updated reader; keep the corresponding software version with an active workspace.

Flag 1.0.x execution path does not use this staged writer. The storage change belongs to version 1.1.0.dev1 enhanced flag/combined execution.

## 7. Clearer interfaces and analysis

The standalone flag interface now exposes the parameter convention and displays bundle rank. Its worker help correctly identifies 0 or 1 as serial; the configured combined flag path uses 0 for automatic allocation, capped at 12. Quotient help distinguishes a fiber-weight consistency check from a justified geometric subbundle embedding.

The enhanced flag workspace adds Hodge, saved-progress, cancellation and spectrum/exponent controls. Its completed-matrix cache distinguishes parameter conventions. Spectrum analysis works at the selected exact Novikov point while preserving the symbolic matrix; omitted values default to one.

The standalone flag GUI substitutes a custom Evaluate y assignment into the returned matrix and suppresses its separate numerical y=1 spectrum. The toric and combined analysis workflows retain their symbolic matrices. See the evaluation table in [Input/output conventions](input-output.md).
